# ADR-014: Testing ownership across plugins; dependency scan in ascent-security, test strategy in ascent-quality, restore proof in ascent-ops

**Status:** Accepted (2026-10-27; built in v0.4.9 to v0.4.11, see decision 6)
**Date:** 2026-10-26 (America/New_York)
**Decider:** lloydbriantech

## Context

`ascent-quality` is rank 4 of the plugin roadmap, "to be scoped when it starts" ([ROADMAP.md](../ROADMAP.md)). Restore and failover proof is a committed follow-up. Three questions came up while scoping it (file and line references are to v0.4.7):

- **Who owns each kind of testing?** Integration, load and performance, user acceptance, operational readiness, launch readiness, navigational integrity and others are spread across plugins, or covered by none. With no rule, a target could be defined in two plugins, or a check could run in two.
- **Where do security scans live?** The first scoping draft put the dependency and vulnerability scan in `ascent-quality`, because `ascent-security`'s skills are generated from the template (ADR-009). The operator rejected that: anything about security, scans or vulnerabilities belongs to `ascent-security`. The packaging constraint does not hold either. `make plugins` and the T1 drift gate only touch files that carry the `<!-- GENERATED by make plugins` marker (`make/build-plugins.sh:42-47`, `make/test-plugins.sh:84-93`).
- **Where does restore proof live?**

[PILLARS.md](../PILLARS.md) lists the gaps:
- **Dependency vulnerabilities: Gap** (`PILLARS.md:65`). The embedded `ascent-dependency-health` is offline and reads only `package.json` (`skills/lloydbriantech-ascent/assets/template/.claude/skills/ascent-dependency-health/SKILL.md:20,31-33`).
- **Version pinning:** exact pinning "is read, not tested" (`PILLARS.md:52`).
- **Functional suitability: Partial** (`PILLARS.md:35`). The rule ("every acceptance criterion maps to a test") lives in the delivery loop's definition of done (`plugins/ascent-delivery/skills/delivery-loop/SKILL.md:106`) and the tester role (`references/role-tester.md:73`). No checker measures it across a repository.
- **Performance efficiency and scalability: Partial, no load test** (`PILLARS.md:37-38`). `quality-attributes` names the measurement and never runs it (`plugins/ascent-architecture/skills/quality-attributes/SKILL.md:82`).
- **Recoverability: Partial; restore and failover proof: Gap** (`PILLARS.md:76-77`). `ops-review` reads a restore-test date (`plugins/ascent-ops/skills/ops-review/SKILL.md:120`). Nothing checks that a drill ran or met `rto` and `rpo` (`plugins/ascent-architecture/references/contract-template.yml:30-31`). `ascent-ops` does not mention failover.
- **Operational readiness** is checked as present (endpoints, SLOs, alarms; `ops-review/SKILL.md:64,142-144`), never exercised.

The operator reviewed the full scoping analysis and accepted every decision below on 2026-10-27. Rule ids follow ADR-015: every family is plugin-qualified.

## Decision

1. **Testing ownership rule.** The plugin that sets a target owns the check. `ascent-quality` owns whether a test exists, runs and asserts that target. Running anything against a live environment is the operator's, from a delivery runbook. Each testing type has up to three owners, and never two copies of one:
   - **Target**, in the project contract, set once by the domain's plugin.
   - **Test present**, checked by `ascent-quality`, or by the domain plugin where the test belongs to that domain (accessibility, navigation and front-end performance stay in `ascent-ux`; drills and readiness exercises stay in `ascent-ops`).
   - **Run live**, by the operator. Claude reads the redacted result.

   | Testing type | Owner | Release |
   |---|---|---|
   | Unit, integration and contract, regression and end-to-end | `ascent-quality` | 0.1.0 |
   | User acceptance: criterion → test traceability | `ascent-quality` | 0.1.0 |
   | User acceptance: sign-off record | `ascent-delivery` | 0.2.0 |
   | Load and performance (server): targets | `ascent-architecture` | exists |
   | Load and performance (server): test present, thresholds equal targets | `ascent-quality` | 0.2.0 |
   | Front-end performance, accessibility | `ascent-ux` | exists |
   | Navigational integrity, cross-browser | `ascent-ux` | 0.3.0 |
   | Smoke | `ascent-delivery` | exists |
   | Operational readiness exercises, restore, failover | `ascent-ops` | 0.3.0 |
   | Launch readiness (go or no-go, conductor pattern) | `ascent-governance` | later (ADR-015) |
   | Dependency vulnerabilities and supply chain | `ascent-security` | 0.2.0 |
   | Security testing (DAST, pen test) | `ascent-security` | later |
   | Mutation evidence | `ascent-quality` | 0.2.0 |

2. **`ascent-security` 0.2.0 adds a hand-written `dependency-check` skill.**
   - This amends ADR-009 decision 1 ("plugin skills are generated, not written"). `ascent-security` becomes a hybrid plugin: generated skills from the template, plus hand-written skills that carry no GENERATED marker. The generated skills keep every ADR-009 rule. The CLAUDE.md plugin rule is updated in the same pull request.
   - **`SEC-D` rules, offline:** lockfiles, pinning (reusing `ops.version_pinning`, `plugins/ascent-ops/references/contract-template.yml`), engine constraints, dependencies from unexpected sources, and licences.
   - **The scan:** `run-vuln-scan.sh` runs `osv-scanner`, `trivy fs`, `npm audit` or `pip-audit` when on `PATH`, and normalises findings to `ID | package | version | severity | fixed-in | file:line`.
   - **Scanners are used, never installed.** An invocation proven to download nothing runs without asking. Any network call needs the operator's agreement, after the `trivy config` precedent (`plugins/ascent-ops/skills/iac-config-check/SKILL.md:26,59`). With no scanner and no agreement, the rule is "unmeasured" (Low), never PASS.
   - **Severity:** a Critical or High advisory with a fix available is High; with no fix, Medium, waivable by ADR; other advisories are Low. A manifest without a lockfile, at standard or enterprise, is Medium. The skill's own marked table (`dep-severity`) is copied into `security-auditor`, and T5 checks it with a `marked_table` line. The shared `security-audit`/`sec-posture` table is unchanged.
   - **Licences** are checked only against a `security.dependencies.licences_denied` list the operator writes. ASCENT ships no default list.
   - `sec-posture` is unchanged, because changing it would change the scaffold. Folding dependencies into the posture rating needs a template change, scoped separately.
   - The embedded `ascent-dependency-health` stays as it is. The plugin skill is its sibling and does not call it.
3. **`ascent-quality` 0.1.0, a hand-written test-strategy plugin with no plugin dependencies.**
   - It uses the hybrid pattern (`references/patterns.md:39-61`).
   - **`quality-review`**: the entry point and the rating (strong, moderate or weak). It loads or proposes the `quality:` section of `.ascent/contract.yml` (detect, don't ask) and runs three lenses: inventory, traceability and hygiene.
   - **`test-inventory`** (`QA-I` rules): which required test types exist (`quality.tests.types_required`), whether CI runs them, and which integration boundaries (database drivers, queue clients, outbound HTTP clients) no test reaches. Boundary detection is a heuristic, reported as Low until trialled.
   - **`test-check`**: criteria to tests and core rules to tests (`QA-T` rules); skipped, focused, assertion-less and retried tests (`QA-H` rules).
   - **`quality-reviewer`**: a read-only agent (Read, Grep, Glob) with an identical copy of the severity table, which T5 checks. The delivery loop's tests lens can use it when installed.
   - **Criterion ids:** the default pattern is `AC-<n>[.<n>]`, overridable through `quality.tests.criteria_id_pattern`. A repository with no ids reports the `QA-T` rules as "unmeasured" (Low).
   - **0.2.0:** load test alignment (the script's thresholds equal `p95_latency_ms` and `peak_rps`, read from `architecture.quality_targets` and never copied) and mutation evidence.
   - **Code health is out of scope.** Coupling and twelve-factor controls go to `ascent-architecture` 0.1.x.
4. **Restore, failover and readiness proof ship in `ascent-ops` 0.3.0**, as a new `recovery-drill` skill and `check-drills.sh`.
   - `OPS-R1`–`OPS-R8` cover recovery: a runbook per backup and recovery path, the runbook standard, a fresh record per path, `measured_rto ≤ rto` and `measured_rpo ≤ rpo`, evidence present and free of credentials, failed drills followed up, the manual's restore date current, and a failover drill when the IaC declares failover.
   - `OPS-X1`–`OPS-X3` cover operational readiness: every paging alarm exercised and reaching a person, the readiness probe failing with a dependency down, and every runbook linked from an alert dry-run.
   - A proof is an operator-run drill runbook that follows `references/runbook-standard.md`, a dated drill record with repo-relative evidence, and targets read from `architecture.quality_targets`. Claude never runs a restore, a failover or an exercise.
   - The checks prove an exercise was recorded consistently. They do not prove it was honest, and the output says so.
5. **Enterprise maturity by default**, as in ADR-011 and ADR-013. Every gap the target requires is Low unless a waiver ADR covers it.
6. **Release order** (after the v0.4.8 ownership registry and id migration, ADR-015): `ascent-security` 0.2.0 in v0.4.9, `ascent-quality` 0.1.0 in v0.4.10, `ascent-ops` 0.3.0 in v0.4.11. The last two may swap if a drill is ready sooner.
7. **Follow-ups recorded in `ROADMAP.md`**, not built here: `ascent-ux` 0.3.0 (navigational integrity, cross-browser), `ascent-delivery` 0.2.0 (UAT sign-off), the launch-readiness conductor (`ascent-governance`, ADR-015), `ascent-quality` 0.2.0, the threat model and DAST under `ascent-security`, outcome-of-change measures under `ascent-delivery`, and coupling controls under `ascent-architecture`. `PILLARS.md` gains a testing section.
8. **Delivery bar**, as for every plugin (`CONTRIBUTING.md:137-143`), per release:
   - hardened source
   - behavior tests in `tests/plugins/<plugin>/` under `/bin/bash` 3.2 and every awk installed, with scanner output recorded as fixtures so no test needs the network
   - negative controls in a new `make/test-mutants.sh` group
   - the plugin gate with the T10 version check
   - a read-only trial, each run in a fresh conversation, with trial repositories never modified
   - a release record

## Alternatives considered

- **The dependency scan in `ascent-quality`** (the first draft). Rejected by the operator: security scans belong to the security plugin, where users look for them and where `security-auditor` can use them. The packaging reason given for it did not hold.
- **The dependency scan as a template skill, generated into `ascent-security`.** Rejected. It would change every scaffold, whose `ascent-dependency-health` is deliberately offline, and scaffolded projects would gain a network-capable skill without asking.
- **`ascent-quality` owns every kind of testing, including navigation, readiness and drills.** Rejected. It would duplicate targets and rules that `ascent-ux` and `ascent-ops` already own, such as the WCAG pass, endpoints, alarms, manuals and the runbook standard, or depend on those plugins at runtime.
- **Test effectiveness traceability alone for `ascent-quality` 0.1.0.** Rejected. Most repositories do not tag tests with criterion ids, so the first trial would mostly report "unmeasured". The `QA-I` and `QA-H` rules add evidence that needs no ids.
- **Code health (complexity, duplication, dead code).** Rejected. It overlaps `design-principles-check` and the embedded `ascent-layering-check`. Complexity counting in awk is heuristic across languages, so its controls would pin heuristics, not rules.
- **Require a scanner (wrap `osv-scanner` or `trivy`).** Rejected, as in ADR-013. They need installing and a database download. The skill uses them when present and reports "unmeasured" when not.
- **Restore proof in `ascent-quality`.** Rejected. Recovery would be split across two plugins.
- **A separate `ascent-resilience` plugin.** Rejected for now. About 800 lines do not justify a plugin, and it would add a fourth reader of `rto` and `rpo`. Revisit if chaos testing is scoped.

## Consequences

- Every new rule or plugin names which of the three owners it is (target, test present, run live) for the testing type it touches.
- `ascent-security` is no longer purely generated. Contributors must check for the GENERATED marker before editing a security skill. Generated skills are edited at the template source; hand-written ones in `plugins/`.
- PILLARS moves as the controls land, with the rows updated in the same pull requests (`PILLARS.md:91`):
  - v0.4.9: dependency vulnerabilities Gap → Partial without a scanner, Strong with one; version pinning Strong for package manifests.
  - v0.4.10: functional suitability Partial → Strong for repositories that tag criteria.
  - v0.4.11: restore and failover proof Gap → Partial; recoverability Partial → Strong; availability gains readiness evidence.
- A live vulnerability result depends on the operator's scanner and its database date. The report prints both, and a scan older than `scan_max_age_days` is "unmeasured".
- Repositories without criterion ids get no traceability evidence until they adopt a convention. The skill proposes one; it does not invent a mapping.
- **(uncertain)** Whether the trial repositories have test suites, lockfiles, real backups and paging alarms. The trials may exercise mostly N/A paths, and the ops trial may need the operator to run a first drill and a first alarm exercise.

## Cost implications

Estimates. `ascent-ops` 0.1.0 was about 2,700 plugin lines, 1,100 test lines and 82 controls (ADR-013).

| Release | Plugin lines | Test lines | Controls |
|---|---|---|---|
| `ascent-security` 0.2.0 | about 1,000 | about 500 | about 25 |
| `ascent-quality` 0.1.0 | about 1,600 | about 700 | about 35 |
| `ascent-ops` 0.3.0 | about 800 | about 400 | about 28, plus one operator-run drill and one alarm exercise for the trial |

- **CI:** one new mutant group per release. Each should stay under the 15-minute job limit at about 7 seconds per control (ADR-013:102), to be measured.
- **Gate:** one `marked_table dep-severity dependency` line in `make/test-plugins.sh`.
- **Recurring:** keep the scanner flag matrix current as the tools change their offline options, and refresh the severity mapping if a scanner changes its scale.
- **Runtime:** bash, awk and git. Scanners only when already installed. Network only with the operator's agreement.
