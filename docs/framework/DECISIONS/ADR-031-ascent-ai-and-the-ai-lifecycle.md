# ADR-031: ascent-ai and the AI lifecycle: the tier record, AI evidence, red-team results, and paid compute and GitHub writes at the operator boundary

**Status:** Accepted
**Date:** 2026-11-25 (America/New_York)
**Decider:** lloydbriantech

## Context

ASCENT checks a project's security, architecture, UX, operations, tests, decisions, documentation and launch readiness with evidence. Until this release it said nothing about the part of a modern product most likely to fail quietly: the AI in it. Teams ship assistants and agents with no baseline to show value, no evals, more autonomy than the job needs and no owner after launch, and nothing in ASCENT noticed.

On 2026-11-22 an outside review of ASCENT against a 12-stage AI lifecycle produced five actions, in this order: a code-review provider ([ADR-032](ADR-032-code-reviewer-and-the-code-review-lens.md)), an AI plugin, red-team evidence, a risk tier, and paid compute at the operator boundary. On 2026-11-25 the operator asked for the AI plugin to cover the practices of a successful and effective AI or agentic application, with no overlap with any other ASCENT review, and for all five to ship in one release so CI runs once.

Three facts shaped the design:
- A repository can hold several AI applications (a support assistant and a screening tool in one monorepo), each with its own risk.
- The tools that produce AI evidence (Promptfoo, garak, lighteval, Ragas) spend money and use provider keys on every run, as deploys do.
- The operator-boundary hook ([ADR-010](ADR-010-delivery-loop-plugin-and-operator-boundary-hook.md)) inspected Bash commands only, so a GitHub write through an MCP tool, such as an inline pull-request comment in GitHub Actions, passed unseen.

## Decision

1. **A new plugin, `ascent-ai` 0.1.0, hand-written, code `AI`.** Skills `ai-design` (recommends a prompt, a fixed workflow or an agent, least autonomy first, and drafts the design record, the `ai:` section and an ADR only after the operator approves), `ai-review` (rates an application strong, moderate or weak by lifecycle stage), and three check skills with scripts: `check-ai-design.sh` (AI-V, AI-M, AI-A, AI-P, AI-K, AI-F: declarations against the code), `check-ai-evidence.sh` (AI-G, AI-E, AI-R, AI-L: result files against targets) and `check-ai-runtime.sh` (AI-O, AI-C: tracing, capture policy, gateway and spend). A read-only `ai-reviewer` agent is the first provider of a new delivery-loop lens, **AI behavior**, which applies when a change touches prompts, tool definitions, model calls, eval files, retrieval code or the `ai:` section.
2. **What counts as an AI application is detected, never asked:** an `ai:` section, a model SDK in a manifest or an import (Python and TypeScript), a `prompts/` folder or `tests/evals/`. Retrieval alone is not one, and neither is test data: `fixtures/`, `testdata/` and `__fixtures__/` folders are skipped like `node_modules`. Claude Code extensions are out of scope. A repository may declare several under `ai.applications`, each with its own root, design record, tier record, results and red-team evidence; every check runs, and scales its severity, per application, and its findings name it. AI code outside every declared root belongs to no application, and GOV-A1 reports it.
3. **No overlap.** Each concern has one owner. AI safety by design and red-team results are `ascent-security`'s; provider keys and pinned packages stay with SEC-D and `env-audit`; the fine-tune runbook's structure is `ascent-ops` `runbook-check`'s; rollout and rollback are `ascent-ops`'; ordinary tests are `ascent-quality`'s, whose scope text now says AI evals are `ascent-ai`'s; hosting cost is `ascent-architecture`'s, and model spend `ascent-ai`'s; the tier is `ascent-governance`'s; code review of the application's code is `code-reviewer`'s. `ascent-ai` takes over the AI behavior evals domain from the template skill `ascent-ai-evals`, which stays in scaffolded projects until Phase 4.
4. **Evidence only.** No checker runs an eval, a red team, a model or a gateway, or calls a network. Tools run from operator runbooks and write result files where the contract says. Checkers take options and never read the contract; `check-audit.sh` builds the options through `lib/adapters.tsv`. Formats read in v1: Promptfoo JSON, `ascent-evidence-v1` (a small file for tools with no stable format, always reported as self-reported, AI-E5), garak `report.jsonl` and `hitlog.jsonl`, and Promptfoo red-team JSON, each verified against the tools' own public fixtures. The golden set lives in `tests/evals/golden/` with a `VERSION` file and four slices (typical, edge, attack, regression) in each test's metadata.
5. **The AI risk tier is a record a person signs** (`ascent-governance` 0.3.0): `docs/governance/ai-tier/<application>.md`, with the tier, who decided, when, a review date and four reasons with fixed values (audience, actions, decisions about people, personal data). GOV-A1–A5 check it: every application has one, it is complete, a person in `approvers` decided it, it is not past review, and the tier is not below what its own reasons imply. GOV-A runs whenever an AI application is detected, above the lowest rung, whatever the floors say. Tier 3 is the base of every AI rule; tier 2 drops one level and tier 1 two, never below Low, except rules marked fixed.
6. **Governance runs the AI checkers per application.** New adapter kinds run a checker once per item of `ai.applications` (`item`), fill an option from the current item (`itemfmt`, `{k|default}`), add options for the other items (`others`), split words, pass the environment asked about and the top rung, and add an option only when a key is set (`when`). With an AI application the default `beta` floor gains `check-ai-design` and the threat model (with SEC-T5), and `prod` gains `check-ai-evidence`, `check-ai-runtime`, `check-redteam` and the `ai-review` review. The adapters pass `--threshold Low` to the four tier-scaled checkers, so a tier-2 Medium finding reaches the verdict as a condition instead of passing.
7. **Red-team results and AI threats in `ascent-security` 0.5.0.** `check-redteam.sh`: SEC-R1 a fresh result in a known format for each application (default 30 days), SEC-R2 no probe category's attack success rate above `security.redteam.max_attack_success` (default 0), SEC-R3 every hit fixed or accepted by an ADR waiver with a review date. They are High scaled by the tier, except prompt-injection and data-leak categories, which are Critical and fixed. `check-threat-model.sh --ai` adds SEC-T5: an entry point for a model input, and threats for prompt injection, sensitive information disclosure, excessive agency and unbounded consumption, each mitigated or accepted. `security-test` never runs garak or `promptfoo redteam`; it writes the runbook step. `security-auditor` gains reading guidance for AI code.
8. **Paid compute is the operator's** (`ascent-delivery` 0.3.0). The hook blocks training, tuning, batch and endpoint jobs (SageMaker, Bedrock, Vertex AI, Azure ML, OpenAI and Together fine-tuning), GPU job platforms (`hf jobs run`, `modal run` and `deploy`, `sky launch`, `runpodctl create pod`) and evaluation and red-team runs (`promptfoo eval`, `promptfoo redteam run`, `garak`, `lighteval`, but their help, version and listing options), with "submits paid compute; the operator runs it from a runbook". A run against a local model is blocked too: there is no allow list.
9. **GitHub writes through MCP tools are the operator's.** `hooks.json` adds a second matcher, `mcp__.*`, running the same hook. A tool `mcp__<server>__<action>` on a GitHub server (`github`, or a server name with `github` joined to other words by `_` or `-`, such as `github_<x>`, `<x>_github` or `github-mcp-server`) is allowed only when its action starts with get, list, search or view; everything else on a GitHub server is blocked. Only the tool name is read, never its input. Other MCP servers pass. This extends ADR-010, which stays as written: an accepted ADR is never rewritten.
10. **Tests and controls.** A behavior-test suite per new script, on three awks and macOS bash 3.2, with fixtures for a passing Python agent, a TypeScript workflow, a retrieval application, a project with no AI and one failing fixture per rule; rule pins in `test-ai-rules.sh`, `test-live-rules.sh` and `test-delivery-rules.sh` D11. Negative controls P1712–P2139 (but ADR-032's P2060–P2087): groups `ascent-governance-ai`, `ascent-ai-detect`, `ascent-ai-design`, `ascent-ai-evidence`, `ascent-ai-runtime`, `ascent-ai-rules`, `ascent-security-redteam` and `ascent-delivery-review` (P2088–P2123 for the hook).
11. **A read-only trial before release.** Detection, the three check scripts and `ai-design` ran read-only on real AI repositories. Every false positive it found was fixed test-first with a control: a Bedrock client counted only with an AWS SDK import, a token limit passed in a variable named near the call, test data skipped, and `ai-design` told to read hand-built loops and notebooks, ask for the baseline on existing code, and rate a read-only tool reversible.

## Alternatives considered

- **AI checks inside `ascent-quality` or `ascent-security`.** Rejected: evals, autonomy, model spend and the improvement loop are neither tests nor security, and either plugin would grow a second purpose. Only AI safety and red-team results went to `ascent-security`, which already owns safety and live testing.
- **One application per repository.** Rejected by the operator: monorepos with several assistants are common, and one tier for all of them would rate a drafting aid like a screening tool.
- **A tier inferred from the code.** Rejected: the tier is a judgement about people and harm. GOV-A5 holds the person's choice to the reasons they wrote; AI-A5 compares those reasons with the tools actually built.
- **Running evals or red teams from the checkers.** Rejected: they cost money and need keys, and evidence-only checks are how QA-L, QA-M, SEC-L and OPS-R already work.
- **Reading MCP tool inputs to allow harmless writes.** Rejected: the shape of each server's input is its own and can change; reading the name is enough to block every write and allow every read, the same shape as the `gh` allow list.
- **An allow list for local-model eval runs.** Rejected for now: the hook cannot tell a local endpoint from a paid one without reading configuration, and the runbook carries the run either way.

## Consequences

- A team with an AI application gets findings on value, autonomy, tools, limits, evals, retrieval, tracing, spend and the off switch, scaled to the risk a person signed for, and a launch verdict that includes them.
- Absent evidence is a finding or not applicable, never a pass.
- Evidence costs the team a runbook step per tool; ASCENT never spends their money.
- A GitHub MCP server registered under a name with no `github` word is not recognized; the README says so.
- `check-ai-design.sh` does not see an agent loop built by hand as a step graph or state machine, or code in notebooks; `ai-design` and `ai-design-check` tell the reader to look for both.
- The template skill `ascent-ai-evals` and `ascent-ai` overlap in scaffolded projects until Phase 4 retires the former.
- Several new adapter kinds make `adapters.tsv` richer and `test-adapters.sh` larger.

## Cost implications

- One new plugin (5 skills, 1 agent, 4 scripts with their libraries, 5 references), three plugins changed, about 430 new negative controls, which add harness time; the plan measured the new groups locally and kept each under the 95-minute guide.
- Every team that adopts it writes a design record, a tier record and a golden set: hours, once, then upkeep with each prompt or tool change.
- Each red-team or eval run costs the team model spend, from their runbook.
