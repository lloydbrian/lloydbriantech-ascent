## Notes

Followed `runbooks/restore-db.md` in podman against a stand-in for the nightly backup: a source database with 200 customers and 1,000 orders, dumped with `pg_dump -Fc` one second before the drill started. The scratch container ran the same image as `compose.yml` (`postgres:16.4`).

- **RTO:** the restore reached a ready database with every row in 2 seconds; recorded as 1m, rounded up as the runbook says. A production dump is larger: measure again when the data grows.
- **RPO:** the dump was one second old at the start, recorded as 1m. With nightly dumps at 02:00 UTC the worst case is 24h, which is the contract's target.
- **Deviation:** the scratch container was named `v0412-drill-db` and the pre-flight archive check ran in the source container, so no throwaway container was removed; the runbook's Rollback was left to the operator.
- **Deviation:** the RTO was measured to a ready database, with no api started against it. The runbook was revised after this drill to start the api and measure to its readiness, to remove the scratch volume and the dump in the post-flight, and to wait for TCP rather than the socket; the next drill follows the revised runbook.
